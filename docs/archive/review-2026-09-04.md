# Code review — Kalam, 2026-09-04

Full read of `src/` (44k lines, 27 modules) plus `Cargo.toml`, the CI workflow
and the doc set. No local Rust toolchain in this sandbox, so this is a
read-and-reason review, not a compiler-assisted one: **nothing here has been
compiled or run**, and every claim is traceable to a file and line so it can be
checked before acting on it.

Findings are ordered by severity, not by file. Each one says what is wrong, why
it matters, and what I'd do about it. Where I think the current code is right
and looks wrong, that is said too — several of the things that first looked
like bugs turned out to be deliberate and documented.

---

## Summary

This is a genuinely well-built codebase, and unusually so for its size. The
things that normally rot at 44k lines are all healthy here: there is no
`unsafe`, no `unwrap()` on any non-test path except five in one function, SQL
is parameterised everywhere that takes user input, the thread seam
(`tasks.rs`) is enforced by the type system rather than by convention, and the
comments explain *why* far more often than *what*. The `docs/pitfalls.md`
practice is doing real work — several classes of bug that I went looking for
had already been found, fixed and written up.

The defects that remain cluster in two places: **untrusted archive handling**
(EPUB extraction, which is the only place the app parses hostile input) and
**a small number of correctness edges** that only appear at boundaries — a
panic on multi-byte text, a timezone assumption in the streak counter, a
session row that leaks on crash.

## 1. Zip-slip — an EPUB can write files anywhere the user can write

**High. This is the one I would fix first.**

`src/epub_book.rs:142`:

```rust
fn extract_zip(epub: &Path, dest: &Path) -> Result<()> {
    for i in 0..archive.len() {
        let mut entry = archive.by_index(i)?;
        let name = entry.name().replace('\\', "/");     // ← attacker-controlled
        ...
        let out_path = dest.join(&name);               // ← no validation
        if let Some(parent) = out_path.parent() {
            fs::create_dir_all(parent)?;               // ← creates the traversal path
        }
        let mut out = File::create(&out_path)?;
        std::io::copy(&mut entry, &mut out)?;
    }
}
```

`entry.name()` is a string chosen by whoever built the EPUB. `Path::join` has
a documented behaviour that makes this worse than it looks: joining an
**absolute** path *replaces* the base entirely. So:

- an entry named `../../../../.config/autostart/x.desktop` escapes
  `~/.local/share/kalam/cache/reader/<uuid>/` and lands in the user's autostart
  directory — arbitrary code on next login;
- an entry named `/home/user/.bashrc` ignores `dest` completely and writes
  straight there, because `dest.join("/home/user/.bashrc") == "/home/user/.bashrc"`;
- `create_dir_all(parent)` helpfully builds whatever directory chain the
  traversal needs before the write.

The trigger is opening a book in the reader, which is the app's primary
action. The EPUB does not need to be malicious in an obvious way — this is the
standard shape of the attack against ebook readers, and EPUBs are routinely
downloaded from strangers.

The zip crate ships the fix. `ZipFile::enclosed_name()` returns `Option<PathBuf>`
and is documented as returning `None` for exactly the paths that can escape:

```rust
let Some(rel) = entry.enclosed_name() else {
    // Skip rather than fail: one hostile entry should not make an
    // otherwise-readable book unopenable.
    continue;
};
let out_path = dest.join(rel);
```

Note this also removes the need for the manual `replace('\\', "/")` — that
line was itself a half-step toward path sanitising and is the tell that the
question was considered but not finished.

Two more things in the same function while you are there:

- **Symlink entries.** The zip format can carry a symlink (unix mode `0o120000`).
  The current code writes its *target string* as a regular file, which is
  harmless — but if that ever changes to honour modes, a symlink to
  `~/.ssh/authorized_keys` plus a second entry writing through it is the classic
  two-step escape. Worth a comment saying the omission is deliberate.
- **`dest` is never cleared first.** A re-extract over a stale cache directory
  merges rather than replaces, so a book that once had a hostile entry keeps it
  after the book is fixed.

Same class, lower reachability: `src/epub.rs:305` (`extract_cover`) writes
`dest_dir.join(&name)` — but `name` there is a locally-derived `cover.{ext}`
from a whitelist, so it is fine. `src/epub_write.rs:86` reads names from the
archive but only ever writes them back into a `ZipWriter`, never to the
filesystem — also fine. `extract_zip` is the only real exposure.

**Add a regression test.** This is precisely the shape `pitfalls.md` §19 warns
about ("a test that passes on a machine where the bug cannot appear"): build a
tiny in-memory zip with a `../` entry, extract to a `tempdir`, assert nothing
exists outside it. That test is headless, fast, and fails loudly on the current
code.

## 2. No bounds on extraction — a 20 KB file can fill the disk

**High, same function.**

`extract_zip` streams every entry with `std::io::copy` and no cap on the
decompressed size, the entry count, or the total. A zip bomb (nested deflate,
~28 MB expanding to petabytes; a flat 42 KB file reaching 4 GB is trivial)
will fill `~/.local/share/kalam/cache/reader/` until the disk is full — on a
laptop that means a wedged session, not just a failed book open.

The user's stated machine is 4 GB RAM and the roadmap already treats memory as
a first-class constraint (`COVER_CACHE_MAX` is justified in exactly those
terms), so this deserves the same treatment:

```rust
const MAX_TOTAL_BYTES: u64 = 512 * 1024 * 1024;
const MAX_ENTRIES: usize = 10_000;

let mut written: u64 = 0;
// ... per entry:
written += std::io::copy(&mut entry.take(remaining), &mut out)?;
if written > MAX_TOTAL_BYTES { anyhow::bail!("EPUB is implausibly large — refusing to extract"); }
```

`entry.size()` (the declared uncompressed size) is a useful cheap pre-check but
must not be *trusted* — it is attacker-controlled and can lie. Cap the actual
bytes copied with `Read::take`, which is what makes it real.

## 3. `truncate_def` panics on any multi-byte character

**Medium — a real crash, easy to hit, one-line fix.**

`src/pages/reader.rs:4297`:

```rust
fn truncate_def(s: &str, n: usize) -> String {
    if s.len() <= n { s.to_string() } else { format!("{}…", &s[..n]) }
}
```

`s.len()` is bytes; `&s[..n]` panics unless `n` falls on a character boundary.
Called at `reader.rs:4189` and `:4224` with `n = 180` on dictionary
definitions and saved-word definitions — i.e. on **imported dictionary
content**, which is exactly where non-ASCII lives (a definition containing an
em-dash, a curly quote, an IPA transcription, or any non-Latin script).

The odds are roughly 2-in-3 that a given multi-byte character straddling byte
180 panics. And because this runs inside the reader's widget-build path, which
is inside a GTK signal callback, the panic **cannot unwind** — it aborts the
process. That is the identical escalation already documented in
`pitfalls.md` §1a; the mechanism was recorded but this call site was missed.

Fix, matching the idiom already used four times elsewhere in this codebase
(`metadata/mod.rs:60`, `book.rs:1601`, `library.rs:707`, `reader.rs:2091`):

```rust
fn truncate_def(s: &str, n: usize) -> String {
    if s.chars().count() <= n {
        s.to_string()
    } else {
        format!("{}…", s.chars().take(n).collect::<String>())
    }
}
```

I checked the other byte-slices for the same bug and they are all safe, which
is worth recording so nobody re-audits them: `db.rs:1201` and `db/history.rs:70`
slice ISO-8601 timestamps (ASCII by construction, and length-guarded);
`dict.rs:358/364/565` slice at a byte offset returned by `find`, which is
always a boundary; `db/dictionaries.rs:874-887` likewise uses `rfind` offsets
and correctly adds `q.len_utf8()`; `epub_book.rs:2432` slices at a `find`
result. `author.rs:763` (`digits[..4]`) is safe only because `digits` is
filtered to ASCII digits first — fine, but it depends on a non-local invariant.

## 4. A reading session leaks a row on crash, and inflates the next total

**Medium — silent data corruption in the analytics the app is proud of.**

`start_reading_session` (`db/history.rs:246`) inserts a row with
`ended_at = NULL, seconds = 0`. `close_session` (`reader.rs:1731`) fills it in
from `shutdown()`. If the process dies — a panic like §3, an OOM kill on the
4 GB box, a power cut, `kill -9` — `shutdown()` never runs and the row stays
`ended_at IS NULL, seconds = 0` forever.

Two consequences:

1. `count_sessions_for_book` counts it, so the book page reports a session that
   contributed no time. Minor.
2. More subtly, the **streak** query (`db/stats.rs:250`) filters `WHERE
   seconds > 0`, so a crashed session does *not* count toward a streak even
   though the user genuinely read that day. A crash silently breaks a streak
   the user earned — and streaks are a feature the roadmap treats as
   motivating.

There is no reaper anywhere: I grepped for `ended_at IS NULL` across `src/`
and there are zero hits. So these rows accumulate for the life of the
database.

Two things worth doing, and they are independent:

- **Reap at startup.** One statement in `migrate()` or next to the reader-cache
  prune: `UPDATE reading_sessions SET ended_at = started_at WHERE ended_at IS
  NULL` — any row still open when the app starts belongs to a session that
  ended when the previous process did.
- **Checkpoint while reading.** The reader already gets a `progress` message
  from the JS bridge on every scroll (`epub_book.rs:436`). Writing `seconds` on
  that tick (throttled — the bridge already throttles at 1% movement) means a
  crash loses at most the last few seconds instead of the whole session. That
  also makes the 6-hour clamp (`db.rs:1119`) less load-bearing.

While in this code: the clamp comment says "laptop suspended with the reader
open", and `session_start.elapsed()` is an `Instant`, which on Linux is
`CLOCK_MONOTONIC` — so it does **not** advance across suspend. The clamp is
therefore protecting against a case that mostly cannot happen, and the real
case (window left open overnight while awake) is the one it catches. The
comment is subtly wrong even though the code is right; worth correcting since
the next person will reason from it.

## 5. "Today" is UTC everywhere, which is wrong for the user

**Medium — visible daily to a user in Asia/Kolkata.**

Every timestamp is written as ISO-8601 **UTC** (`format_unix_utc`, `db.rs:1392`)
and every day-bucket is `substr(started_at, 1, 10)` — i.e. the UTC date.

For a user at UTC+05:30 (the repo's own timezone), reading between 00:00 and
05:30 local is filed under the **previous** day. That breaks, concretely:

- **Streaks** (`db.rs:1192`) — reading at 1 a.m. every night registers as the
  day before; `today - nums[0] <= 1` still mostly saves the "current" streak,
  but the day *boundaries* are shifted so a genuine gap can look continuous and
  a genuine streak can look broken.
- **The 14-day chart** and `book_seconds_by_day` — bars are attributed to the
  wrong day, and the rightmost bar is empty for the first 5.5 hours of the
  user's day.
- **`iso_days_ago`** (`db.rs:1259`) snaps to UTC midnight, so "last 7 days" is a
  window offset by 5.5 hours from what the user means.

Storing UTC is right and I would not change it. The bug is *bucketing* in UTC.
The fix is to apply the local offset when converting an instant to a day, in
the one place that does it. There is no `chrono`/`time` dependency (deliberate,
and the hand-rolled `days_from_civil`/`civil_from_days` are correct
implementations of Howard Hinnant's algorithms — I checked them against the
reference), so you would read the offset once at startup via
`localtime_r`/`TZ`, or add `time` with default features off.

This is a design decision, not just a fix, so it belongs in
`docs/conversation.md` before it is coded: **local-day bucketing, UTC storage**
is the standard answer, and it needs a migration note because existing rows
were bucketed the old way.

## 6. `import_sqlite_pack` can panic on a hostile or odd dictionary pack

**Medium.**

`src/dict.rs:284-301` — the only non-test `unwrap()`s in the codebase outside
tests. They are individually safe: each is guarded by an `any()` immediately
above, so the `find()` cannot return `None`. The pattern is `if any(pred) {
find(pred).unwrap() }`, twice-searching but sound.

The real hazard is two lines below:

```rust
} else if cols.len() >= 2 { &cols[1] } else { &cols[0] }   // ← def_col
```

and, for `word_col`:

```rust
} else { &cols[0] }                                        // ← panics if cols is empty
```

`cols` comes from `PRAGMA table_info(<table>)` on a user-supplied SQLite file.
A table with **zero columns** is not constructible in normal SQLite, but
`PRAGMA table_info` also returns zero rows for a **virtual table whose module
is not loaded** — which a crafted or merely unusual pack can contain, and
`chosen` may well be that table since the fallback is "whatever is first in
`sqlite_master`". Then `&cols[0]` panics, in a worker thread
(`settings.rs:416`), which by default aborts nothing but kills the import with
a backtrace instead of the friendly error the surrounding code takes such care
to produce.

Cheap fix, and it removes the `unwrap()`s at the same time:

```rust
let pick = |names: &[&str]| cols.iter().find(|c| names.iter().any(|n| c.eq_ignore_ascii_case(n)));
let word_col = pick(&["word", "term"]).or_else(|| cols.first())
    .ok_or_else(|| anyhow!("dictionary table {chosen} has no columns"))?;
let def_col  = pick(&["definition", "meaning", "def"]).or_else(|| cols.get(1)).or_else(|| cols.first())
    .ok_or_else(|| anyhow!("dictionary table {chosen} has only one column"))?;
```

Also worth noting for the same function: it loads **every entry into a
`Vec<(String, String)>` before writing any**. A 500k-entry WordNet-class pack
is a few hundred MB resident, on a 4 GB machine, in a worker whose progress
reporter (`settings.rs:426`) only ever reports `step(0, 1, name)` — so the user
sees one "Importing…" toast and no movement for the whole import. Streaming in
chunks of 2,000 (the size `install_bundled_dictionaries` already uses at
`dict.rs:151`) would fix both the memory and the progress, and the batching
helper already exists.

## 7. `hydrate_books` interpolates ids into SQL

**Medium — not exploitable today, but it is the one place the parameterisation
discipline is broken, and it is on the hottest path.**

`src/db.rs:1131`:

```rust
let ids: Vec<String> = books.iter().map(|b| b.id.to_string()).collect();
let sql = format!("... WHERE bt.book_id IN ({}) ...", ids.join(","));
```

The values are `i64`s from the database, so no injection is possible and the
comment correctly explains why it is not `prepare_cached`ed. I would still
change it, for two reasons that are about the future rather than the present:

1. **Every other dynamic-length `IN` in this codebase uses placeholders** —
   `db.rs:926` and `db/history.rs:158` both build `({holders})` and bind. This
   one is the odd one out, and an inconsistency in a security-relevant pattern
   is how the next one gets written wrong. The `holders` idiom is already
   there; use it.
2. It defeats the statement cache on the single most-called query in the app
   (every grid, every list page, every snapshot), producing a distinct SQL
   string per call — which the comment acknowledges as a deliberate cost, but
   the placeholder version gets caching back for the common small-N cases if
   you bucket the placeholder count.

Related and worth a look while there: `hydrate_books` is called with **all**
books for a page, and `db/shelves.rs:212/227` + `count_matching_rules` build
per-shelf SQL from rule sets. Those genuinely cannot be cached and are
correctly parameterised (`escape_like` + `ESCAPE '\'` are both right, and I
verified `like_escape_suffix` only emits the clause for the two `LIKE`
operators). No issue there — noting it so it is not re-reviewed.

## 8. The catalog is opened three times before the window appears

**Low, but it is startup cost on the one metric A0 is chasing.**

`main.rs` opens `Catalog::open()` at line 98 (`startup_theme`), then again at
line 74 as the "can we even start" check, and `AppModel::init` opens a third
(`app.rs:836`). Each one runs `migrate()`, which executes the full
`CREATE TABLE IF NOT EXISTS` batch, ~8 `PRAGMA table_info` probes via
`add_column_if_missing`, two `COUNT(*)`s over `dict_entries` and
`combined_words`, and `backfill_dict_entry_keys`.

Measured `startup_db_open` is ~6 ms, so this is ~12 ms of pure waste — small,
and the roadmap's own numbers say the DB is not the bottleneck. But it is
avoidable by opening once in `main()` and passing the `Arc<Catalog>` into
`AppModel` as `Init` (which is currently `()`), and it removes a genuine
correctness wrinkle: three `Connection`s to the same WAL database means the
`COUNT(*)`-guarded `rebuild_combined_dictionary` in `migrate()` can race with
itself on first launch. Unlikely, harmless if it happens (the rebuild is
idempotent), but it is a race that need not exist.

## 9. `change_token` will wrap, and the page cache with it

**Low, but the failure is silent and confusing.**

`db/stats.rs:74` returns `conn.total_changes() as i64`. In `rusqlite` 0.32
`total_changes()` returns **`i32`** (it wraps `sqlite3_total_changes`, not the
64-bit variant). After ~2.1 billion row changes it wraps to negative and keeps
counting.

The consequence is not a crash: `app.rs:631` compares tokens for equality, so a
wrap means one spuriously-equal comparison and one stale page. Getting there
needs 2.1e9 writes, which a personal library will not reach — but the
dictionary importer writes one row per entry, and a user who repeatedly
imports and removes six-figure packs is doing millions per session, not
billions. It is not reachable in practice; it is reachable in principle, and
the fix is `total_changes64()` if the binding exposes it, or a note saying the
wrap is accepted.

More interesting is what the token is used *for*, see §12.

## 10. CSV export: correct quoting, no formula guard

**Low.**

`saved_words_csv` (`pages/saved_words.rs:489`) routes fields through
`csv_field()`, so quoting is handled. But a definition or context beginning
`=`, `+`, `-` or `@` is interpreted as a **formula** by Excel and LibreOffice
on open. Dictionary text starting with `-` is entirely ordinary (`-ing`,
`-ness` are real headwords, and many packs write definitions as `- to do X`).

This is CSV injection. The impact here is mild — it is the user's own machine
and their own data — but the fix is one line (prefix a `'` when the field
starts with one of those four characters), it is what every serious exporter
does, and the export is advertised as an interop feature, so the file will end
up in a spreadsheet.

The Anki TSV (`:507`) is fine: it strips tabs and Anki does not evaluate
formulas.

## 11. `find_zip_index` is O(n) and called once per candidate

**Low, cosmetic, easily fixed.**

`epub.rs:333` scans every entry in the archive comparing names, and
`extract_cover` (`:293`) calls it up to three times (three path candidates) —
so a 2,000-entry EPUB does up to 6,000 name comparisons *and* rebuilds a
`String` per comparison (`.replace()` + `.to_ascii_lowercase()` inside the
loop). It happens once per import, so it is invisible; but the fix is to build
the lowercase name→index map once before the candidate loop, and it removes
two allocations per entry.

Same file, same spirit: `parse_epub_meta` opens the archive, and
`extract_cover` opens it **again** from scratch (`:284`). One archive handle
threaded through would halve the zip parsing at import.

## 12. The page cache is all-or-nothing on any write

**Low — a design observation rather than a defect.**

`app.rs:631` compares `catalog.change_token()` and, on any difference,
`self.cache.clear()`. The comment justifies it well ("no write path has to
remember to invalidate"), and that is the right trade for correctness. But the
token is `total_changes()`, which counts **every** row change anywhere — so
saving reading progress on a scroll tick (`reader.rs:1718`, which fires on
every 1% of movement) invalidates the Home page, the Library dashboard, the
shelves grid and Settings.

In practice that means the cache is empty essentially all the time during
normal use, which is the opposite of its purpose: it exists because
"revisiting Home or Library reconstructed dozens of widgets and re-ran their
queries", and reading a book for ten minutes guarantees exactly that on the way
back out.

I would not redesign this now — A0's measurements say page construction is
~137 ms and not the bottleneck — but it is worth knowing that the cache is
probably not earning its keep, and it is a candidate for deletion (simpler) as
much as for refinement (per-table tokens). Measuring the hit rate would settle
it in one session: a `timing::note("page_cache_hit", ...)` in `take_or_build`.

## 13. 25 `#[allow(dead_code)]` escapes

**Info.**

CI runs `clippy --all-targets -- -D warnings`, which is strong, and
`pitfalls.md` §9 records the lesson that dead code fails the build. The
consequence is 25 `#[allow(dead_code)]` markers, several of them at
**module** level (`db.rs:2`, `shelf_rules.rs:21`) rather than on individual
items — and a module-level allow silences the lint for everything in a
2,200-line file, including code that becomes dead later.

That is the wrong granularity. The narrow ones on `pub struct` fields (e.g.
`Annotation`, `SavedWord`) are defensible — those are data shapes whose fields
are read by some pages and not others. The two module-level ones are not: they
turn off a lint the project deliberately made fatal, across the two files most
likely to accumulate orphans. Worth converting to per-item allows, which will
probably surface a handful of genuinely dead functions.

`source-seam.md` §9 already flags this as a constraint on landing the `Source`
trait ("an unimplemented trait either fails `-D warnings` or adds to the 28
existing escapes"), so this is a known cost — but the module-level allows make
the count misleading, since they hide an unknown number more.

## 14. Test coverage is inverted relative to risk

**Info, and the most valuable structural change available.**

231 `#[test]`s is a lot, and the ones that exist are good — the `CoverCache`
eviction tests, `shelf_rules` compilation, `fold_key` normalisation and the
`snapshots_are_send()` compile-time assertion are all testing the right things
in the right way (particularly the generic-over-`T` trick that makes the cache
testable without a GTK display).

But the distribution is upside down:

| Area | Lines | Tests |
|------|-------|-------|
| `db/dictionaries.rs` | 1,983 | 42 |
| `db.rs` | 2,200 | 35 |
| `service.rs` | 1,184 | 30 |
| **`epub_book.rs`** | **3,342** | **0** |
| **`pages/reader.rs`** | **4,353** | **0** |
| **`epub.rs`** | **507** | **0** |

The two largest files, which between them hold the EPUB parser, the zip
extractor, the injected JavaScript shell and the entire reader, have **zero**
tests — and they are also where findings §1, §2 and §3 live. That is not a
coincidence: those are the modules where a bug survives.

Much of `epub_book.rs` is genuinely hard to test (it needs a WebView). But the
parts that matter most are pure functions and need nothing:

- `extract_zip` — takes two paths, needs a `tempdir` (§1, §2)
- `find_opf_path`, `parse_opf_spine`, `parse_nav_html`, `parse_ncx`,
  `spine_index_for`, `join_zip_path`, `parent_zip_path`, `strip_tags` — all
  string in, data out
- `epub.rs`: `parse_opf`, `percent_decode`, `collapse_ws`, `strip_html`,
  `guess_image_ext` — likewise

That is maybe 15 tests covering the app's only untrusted-input parser. I would
rate this above every Low finding above.

**This also resolves A0 step 7.** The roadmap says step 7 needs reshaping
because CI timings swing 60% and a time threshold cannot catch anything under
a 3× regression — that diagnosis is correct. The recommendation already
recorded there (assert **query counts**, not milliseconds, and un-`#[ignore]`
the two `perf.rs` probes) is the right call and I would just do it: query
counts are machine-independent, they catch the N+1 class that has bitten three
times per `pitfalls.md` §16/§18, and `Connection` can count statements without
any timing at all.

## What is notably good

Worth recording, because a review that only lists faults gives a false
impression of the codebase — and because these are patterns to keep.

- **`tasks.rs` is the best module here.** The `Send`/`!Send` split makes
  "worker code cannot touch a widget" a compile error rather than a rule. The
  two-channel design (`Update` separate from `T`) so `Reporter` stays
  non-generic is a real insight, and the sequential drain-then-result in the
  local future — with the comment explaining that two concurrent futures would
  race and leave a stale progress toast — is the kind of thing normally learned
  from a bug report.
- **Error-path discipline.** `conn()` recovering from a poisoned mutex rather
  than aborting, `main()` failing *before* `app.run()` so a corrupt database
  produces one readable line instead of `Aborted (core dumped)`, and
  `epub_write.rs` verifying the rewritten archive **before** `fs::rename` over
  the user's only copy — that last one is genuinely careful engineering.
